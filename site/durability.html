Durability

You choose how much a crash can lose. Redis RDB and AOF files are not readable. The formats are Ruvio's own: WAL magic RUVWAL01, snapshot magic RUVSNP01.

Profiles

ProfileWhat a crash can lose
memoryThe whole dataset. This is the default. No WAL.
snapshotWrites since the last completed checkpoint.
everysecAbout one sync interval. The client is acknowledged after the append, and the file is synced on sync_interval_ms (default 1000).
alwaysThe record is synced before it is applied and before the reply.

Making always fast on Linux

always has to wait for the disk, so Ruvio does three things to keep that wait short. They need no setting except the first, which defaults to on where it helps.

  • Group commit. All clients whose commands arrived together share one fdatasync; replies are sent after it returns.
  • Sync worker (sync_worker = auto | on | off, see Configuration). The fsync runs on a helper thread, so the shard keeps serving other clients while the disk works. auto enables it on Linux with always, one shard and no hot_keys. If the disk fails or fills, reads and PING are still answered and writes return MISCONF; no acknowledged key is lost.
  • Zero-filled WAL segments (Linux). The WAL file is extended in 4 MiB chunks that a helper thread fills with real zeros ahead of the write position. Syncing blocks that already hold data costs about 0.8 ms instead of 2.0 ms on ext4 with a network SSD, because the filesystem does not have to convert unwritten extents. On a full disk or a filesystem without fallocate the WAL falls back to growing the file.

Measured against Redis appendfsync always on a 4-core Linux VM with a Premium SSD data disk: 1.5 to 2.7 times Redis, depending on clients and pipelining (Performance). A single shard is the recommended shape for always: with more shards the flush latency of the disk, not shard CPU, is the limit.

Validate, record, apply, reply

  1. ValidateThe command is checked before anything changes.
  2. RecordIn WAL-backed profiles the change is appended to the WAL. Under always it is synced before it is applied.
  3. ApplyThe in-memory value is updated.
  4. ReplyThe client gets its answer.

If the log cannot accept the record, the in-memory value stays as it was. Further mutations on that shard return MISCONF.

WAL-backed profiles take an exclusive lock on <data_dir>/LOCK before they listen.

On disk

  • LOCK — one owner of the directory.
  • CURRENT — the published checkpoint generation.
  • CLOCK — the last-seen clock floor.
  • checkpoints/<generation>/ — shard snapshots and a manifest. Digests are BLAKE3.
  • wal/shard-NNNN/ — per-shard segments. Records carry CRC32C.

ruvio-ctl check and inspect read those files without taking LOCK and without truncating a torn tail. ruvio-ctl backup locks the source and copies CURRENT, CLOCK, checkpoints/, and wal/. restore refuses a destination that already has those files unless --force is set.

Checkpoints

SAVE and BGSAVE publish a checkpoint on the shard worker, write CLOCK, then delete WAL segments covered by that checkpoint. BGSAVE does not fork. It does the same in-process work and replies Background saving started after the work completes.

snapshot_interval_ms schedules a checkpoint after that interval when at least snapshot_min_mutations mutating commands have run. 0 mutations means any mutation. snapshot_interval_ms = 0 disables the scheduler. SAVE still works. Recovery uses max(CLOCK, checkpoint.created_at) so TTLs do not look expired if the wall clock moves backwards.

Hot keys in the checkpoint

A matching hot_keys glob is a process-wide string, not a shard key. SAVE writes that partition into the same checkpoint (shard id equals the shard count). Recovery loads it. Enable the prefix on empty data. Existing shard keys are not migrated.
