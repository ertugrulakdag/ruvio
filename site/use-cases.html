Use cases

Ruvio speaks RESP, so any Redis client can talk to it. What sets it apart is a set of commands that finish a coordination job on the shard that owns the key, in one call. This page shows the jobs people reach for, with the commands as you would type them in redis-cli. Each section links to the exact reference.

Rate limits and quotas

A fixed window per API key, per user, or per tenant, in one command on the shard that owns the key.

LIMIT api:key-7 100 60000
# 99   -> 99 calls left in this 60 s window
# (nil) -> window is full, nothing was counted

LIMIT key max window_ms returns the remaining allowance, or a null bulk when the window is full. A rejected call is not counted. The window is the key's deadline, so a quiet key disappears by itself. In WAL-backed modes the accepted call is a log record.

Fixed window, not sliding. If you need per-second smoothing on top, keep a short second window next to the long one. LIMIT

Locks, leader election, and fencing

One worker at a time holds a named resource; others get a null reply until it frees or expires.

LEASE job:nightly-report 30000
# 17      -> you hold it, token 17
# (nil)   -> someone else holds it
RELEASE job:nightly-report 17
# 1       -> released (0 if the token no longer matches)

Each grant returns a token that grows. Send it with writes to the thing you protect and have that side reject older tokens. Expiry and RELEASE keep the sequence while the key exists.

Deleting the key restarts the token at 1, and data loss can do the same. A token alone does not fence an external system after that. LEASE

Concurrency limits for workers

At most N holders at once: image resizers, export jobs, calls to a slow upstream.

SEMAPHORE upstream:billing 8 15000
# 1700000000123 -> a slot, this is your token
# (nil)         -> all 8 slots are taken
RELEASE upstream:billing 1700000000123

Every holder has its own TTL, so a crashed worker frees its slot when the TTL ends. The key is removed when the last holder leaves.

Pick a TTL longer than the longest normal job, and release as soon as you finish. SEMAPHORE

Inventory, tickets, and seat counts

Sell from a counter without overselling, with no script and no read-then-write race.

SET stock:ticket-42 500
TAKE stock:ticket-42 2
# 498   -> took 2, 498 left
# (nil) -> not enough, the key is unchanged

INCRBY seats:room-9 1 MAX 120
# 57    -> joined
# (nil) -> room is full, nothing was written

TAKE subtracts only when the key holds enough. INCRBY … MAX adds only while the result stays at or below the cap. Both answer with a null bulk and write nothing when they refuse.

A refused call writes nothing, neither to the key nor to the WAL. TAKE · INCRBY MAX

Idempotent APIs and payments

A retry of the same request replays the stored answer instead of running the handler again.

IDEM order:42 BEGIN request-digest attempt-1 60000
# ["acquired"]            -> run the handler once
IDEM order:42 COMPLETE request-digest attempt-1 saved-result
# 1
IDEM order:42 BEGIN request-digest attempt-2 60000
# ["completed","saved-result"]

BEGIN answers acquired, pending, conflict (same key, different fingerprint), or completed with the saved result. For plain once-only work such as a webhook delivery id, ONCE key ttl_ms is the lighter tool: 1 the first time, 0 until the deadline.

This does not make an outside effect exactly-once. A handler can crash before COMPLETE, so the payment provider still needs its own idempotency key. IDEM · ONCE

Lost-update protection

Two editors open the same record; only the one holding the current version may save.

SETV profile:ada "{...}"
# 1     -> version 1 created
SETV profile:ada "{...}" 1
# 2     -> accepted, now version 2
SETV profile:ada "{...}" 1
# error -> stale version, value unchanged

Optimistic concurrency without WATCH or a script. Only keys written with SETV carry a version.

A plain SET replaces a versioned string. SETV

Sessions and sliding expiry

Reading a session keeps it alive; an idle one expires on its own.

SET session:9f3 "{...}" PX 1800000
GETEX session:9f3 1800000
# "{...}" and the deadline is now 30 min from now

GETEX returns the string and moves its deadline in one step, so there is no separate EXPIRE call. GET does not move a deadline.

GETEX

Cache fills without stampedes

When a hot key expires, one caller refills it and the others wait or serve the stale copy.

FILLGET product:42 5000 WAIT 200
# [HIT, value]            -> served from memory
# [FILL, token]           -> you refill it
# [BUSY, nil]             -> someone else is filling
# [STALE, value, token]   -> inside a stale-while-revalidate window
FILLSET product:42 "{...}" 60000 <token> SWR 30000
# 1 -> stored (0 if the token is no longer live)

One round trip decides who loads from the database. WAIT holds a caller that would get BUSY until the filler writes, so there is no retry loop in the client.

Fill markers live in memory only and lapse after fill_ms. WAIT is refused inside MULTI and scripts. Commands

Delayed jobs and queues

Schedule work for later with a stream and a consumer group, without a separate scheduler.

XGROUP CREATE jobs workers $ MKSTREAM
XADD jobs DELAY 30000 * kind send-reminder user 42
XREADGROUP GROUP workers w1 COUNT 10 BLOCK 5000 STREAMS jobs >
# the entry appears here after 30 s
XACK jobs workers <id>

The entry is stored right away. XREADGROUP skips it until the delay passes, and XREAD can still see it. Pending entries, XCLAIM, and XAUTOCLAIM work as in Redis streams.

The hold is a WAL record and is written only when a delay is set. XADD DELAY

Change feeds

React to writes (cache invalidation, search indexing, audit) by reading a feed instead of polling.

CHANGES SUBSCRIBE FROM NOW MATCH user:* TYPES put,del
# a durable stream of changes, resumable with FROM <shard>:<seq>

The durable feed is built from the WAL and can resume from a saved position, with optional key patterns, types, and values. CHANGES START is the lighter in-memory feed of up to 1024 notes per shard.

See Change stream in CONFIGURATION.md for limits and retention. CHANGES

Leaderboards, geo, and documents

The data types you already use, plus JSON documents with an exact-match index.

ZADD leaderboard 1200 ada 980 grace
ZRANGE leaderboard 0 9 REV WITHSCORES
GEOSEARCH cities FROMLONLAT 13.36 38.11 BYRADIUS 50 km COUNT 10
JSON.SET user:7 $ '{"plan":"pro","country":"TR"}'
JSON.INDEX CREATE by_plan PREFIX user: PATH $.plan TYPE string
JSON.FIND by_plan VALUE pro COUNT 20

Strings, lists, sets, hashes, sorted sets, streams, geo, Bloom filters, and JSON are covered. JSON.INDEX is an exact-equality index on one scalar field; it works on database 0 and keeps its postings in memory.

Moving from Redis

Ruvio is not a full Redis clone. It speaks RESP2 and covers the commands listed in the command reference. Check that the commands you use are there before you switch. ruvio-ctl import copies keys with their TTLs from a running Redis and can verify the copy. It does not move consumer groups, Lua scripts, ACL users, or module types.

Start with Start, then pick a client. For durability modes and what each one promises, see Durability.
