Clients

Ruvio has first-party clients for six languages. Every one covers all 287 commands in the compatibility matrix with a typed method, plus the options only Ruvio has (SET ... IFEQ, DELEX, FILLGET, LIMIT, Bloom, JSON.FIND and the rest).

A test in each client reads the matrix and fails when a command has no method. Each client has its own page in the Clients menu.

All numbers on these pages come from short runs on a shared 4-vCPU virtual machine, client and server on the same host, over loopback. They show relative cost and allocation, not release-grade throughput.

What they share

The same behaviors, in the idiom of each language:

  • One seed address. The client asks CLUSTER SLOTS, opens one connection per shard and routes by slot. A standalone server answers "cluster mode is disabled" and the client then works as a plain client.
  • MGET, MSET, DEL, UNLINK, EXISTS and TOUCH across slots are split per slot, sent in parallel, and the replies come back in your order. Other cross-slot calls fail before anything is sent.
  • MOVED repairs the slot table and the command is retried once. A command is never replayed after a transport failure.
  • Pipelines, MULTI/EXEC with WATCH, Pub/Sub on its own connection, blocking commands that do not stall the shared connection, and a generic execute for anything else.
  • Binary-safe values, server errors as typed errors, and nil replies as null, None, Optional or a second return value.

Not shared: the Rust client is blocking only, and the Rust and C# clients have no TLS today. No client handles ASK redirects or replica reads. Each page has the full list.

Built for speed and low memory

Users reach Ruvio through a client, so the clients follow the same rule as the server: no work that is not needed. All of them use these ideas, first proved in the C# client:

  • One shared connection. Concurrent callers share a socket and a first-in first-out queue of pending replies. There is no connection pool to size.
  • Write coalescing. Frames that are queued while a write is in flight leave in one write, up to 64 KiB. There is no timer and no batching delay; a lone call is sent at once.
  • Pre-encoded commands. Command names are stored as finished RESP fragments ($3\r\nGET\r\n). Integers are written straight into the output buffer.
  • In-place parsing. Replies are parsed from a reusable read buffer. An integer or +OK allocates nothing; a bulk allocates only the value you get back.

Cluster

Start a three-shard server with shards = 3 and port_mode = "per-shard". Shard i listens on the base port plus i. Give any client one address and it finds the rest. Each page has a cluster example that was run against such a server. Database 0 only; there is no failover, ASK or live resharding in the server, so none of the clients handle them.

Status and gaps

  • The repository holds all six. Only the Rust crate and the NuGet packages are on a registry, and those versions are older than the repository. Registry releases for the rest are not set up yet.
  • Cluster routing was tested on a three-shard server on one machine, not on a real Redis Cluster and not under failure.
  • Some commands were checked only up to the server's reply (ACL file commands without an ACL file, cluster commands on a standalone server). Each page says which.
  • Continuous integration for the new clients is not set up yet.

Which one to use

Use the client for your language. For .NET also look at the integration packages (distributed cache, rate limiting, idempotency, output caching, data protection, distributed lock). For examples of the commands themselves, see Commands and Examples.
