Concurrency, durability and Ruvio shards

Result: With pipelining and 200 clients Ruvio is 1.11–1.43× Redis with the lower p99. always (fsync) durability is where Ruvio leads most: 2.67× at 50 clients, 1.50× at 200 clients and 2.33× at pipeline 16. Two changes since the last run explain it: the WAL fills each preallocated chunk with zeros ahead of the write cursor on a helper thread (an fdatasync of written blocks cost 0.8 ms instead of 2.0 ms on this disk), and a sync worker lets the shard keep executing while the sync runs.

The un-pipelined rows are client-bound: the load generator tops out near 110–120k req/s on this host for both servers (identical GET numbers), so they show the p99 tail, not server capacity. More Ruvio shards lift pipelined SET from 1.14M to 1.33M req/s at 2 shards; at 4 shards the client, which shares cores with the shards, is the limit.

With always, 2 shards and 200 clients at pipeline 16 Ruvio is at parity with Redis (1.00×): extra shards do not help there because disk flush latency, not shard CPU, is the limit.
