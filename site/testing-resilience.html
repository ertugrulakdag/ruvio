Durability and recovery

OverviewCorrectnessPerformanceMemory & TTLResilienceIntegrations

Fault-injection results show behavior in the tested failure model. A process kill or a container filesystem fault is not physical power-loss certification.

Advanced resilience tests · October 2026

scripts/model_check.py is a model-based randomized checker. It starts the real ruvio binary and drives it like this:

  • Several client connections send random commands over a small keyspace, so commands often touch the same keys. One of the connections is an ACL-limited user.
  • A reference model computes the expected reply to every command. Live replies are compared with it as they arrive.
  • Commands running at the same time never share a key, so each key has one known order of operations. Commands on different keys overlap freely.
  • Each epoch ends with a crash, a restart, a live check or an injected fault. After every restart the checker searches for a consistent cut of the acknowledged history that explains the recovered keyspace.

The workload covers strings and counters, key and field TTLs, lists, hashes with field TTLs, sets, sorted sets, streams, MULTI/EXEC, EVAL, RENAME, FLUSHDB, SAVE and BGSAVE, BLPOP with a pusher, and commands the ACL user is not allowed to run.

When a recovered keyspace passes

RuleMeaning
Prefix per keyEach key's value equals the model after some prefix of that key's operations
All or nothingA write that touched several keys (MULTI, EVAL, RENAME, FLUSHDB) is either fully present or fully absent
No holesIf an included write was sent after another write on the same shard was acknowledged, the earlier write is included too
No resurrectionDeleted or expired keys do not come back
Profile boundThe durability profile sets how much acknowledged history must survive (see below)
ProfileRecovered state after a crash must contain
memoryNothing: the keyspace is empty after a restart
everysecEvery write acknowledged before the last sync window
alwaysEvery acknowledged write
snapshotEvery write acknowledged before the last successful SAVE

A clean shutdown (SIGTERM) must keep every acknowledged write in every profile except memory.

Torn WAL writeThe server dies after writing a random prefix of one WAL write. Most tears wait for an idle server, send one MULTI of writes or a RENAME, and cut the first, second or third WAL write after it, so a crash can land between the records of one multi-key writeeverysec, always
Replica crashkill -9 or SIGTERM of the replica, then restart while the primary keeps its dataReplica configs
Memory pressureA maxmemory limit with the noeviction policy that the workload reaches, so writes are refused with OOMmaxmemory

What the checker verifies

CheckFailure it reports
RepliesAny reply that differs from the reference model
Recovered stateNo consistent cut of acknowledged writes explains the keyspace, or the profile bound is not met
No OK after a failed syncA write acknowledged after a WAL fsync failed on its shard
Sticky refusalA shard accepts writes again after a WAL fsync failure, even once the disk recovers; it must refuse writes until restart. After a failed write (not sync), writes must resume once the disk recovers
SAVESAVE replies OK although a checkpoint write or sync failed while it ran; SAVE fails without a fault
HangsCommands get no reply during or after a disk fault
Replica convergenceThe replica does not reach the primary's state in time. Converged also means the same DBSIZE: reads hide a logically expired key, but a replica keeps it until the primary's delete arrives
AtomicityPart of a MULTI, EVAL, RENAME or FLUSHDB is recovered without the rest
Memory limitA command that only frees memory (DEL, UNLINK, LPOP, HDEL, SREM, RENAME and similar) is refused with OOM
CrashesThe server exits on its own

A failure writes a repro directory with the seed, the command to repeat the run, the expected and actual state, the last commands with their replies, and the server log, config and fault log.

Checking the checker

A checker that passes everything proves nothing, so its ability to find bugs is measured.

Mutation testing: scripts/model_check_mutants/ holds 12 patches, each a small, realistic bug planted in the server. A runner applies each one to a scratch worktree, builds it, and runs the checker with fixed seeds over the configurations where the bug can show. The unmodified server is run the same way as a control. In the latest measurement (October 2026: three seeds of 60 seconds per bug, plus tear-heavy runs for the multi-record bugs) the checker catches 10 of the 12.

Planted bugCaughtBy
always acknowledges a small batch before its fsyncYesPower-loss simulation
A failed WAL fsync is treated like a failed write and writes resumeYesSticky-refusal probe after a sync fault
Keys removed by active expiry are not logged as deletesYesRecovered state and replica convergence
A push onto an existing list is missed by a running checkpointYesRecovered state after restart
SAVE replies OK when its checkpoint failedYesSAVE check under a checkpoint fault
EXEC logged as one record per command instead of one transactionYesTorn WAL writes (atomicity)
INCR from 9 returns 11YesLive reply comparison
Shutdown skips the final checkpointYesRecovered state after SIGTERM (snapshot)
HSET stores fields before an OOM refusalYesLive replies and recovered state under maxmemory
Hash field TTLs dropped when a checkpoint is loadedYesRecovered state after restart
RENAME logged as a delete plus a setOnly in tear-heavy runsTorn WAL writes; a default mix rarely cuts between the two records
A reconnecting replica applies its last frame twiceNoNeeds a replication link drop without a process restart, which the fault model does not produce

False alarms: on the unmodified server the checker's false-alarm rate is about 0.7 per hour of run time. Every known cause has been fixed in the checker.

Seeded smoke tests: tests/model_check_live.rs runs a short seeded checker session that must pass, and a run against a server that loses writes, which must be reported as a state failure.

Redis comparison: reply differences the checker found were compared with Redis and fixed to match: a command refused inside MULTI (for example by ACL) now aborts the transaction with EXECABORT; MOVE and SWAPDB with invalid arguments inside MULTI are queued and fail only at EXEC; and a push that wakes a blocked BLPOP client replies with the list length before the hand-off.

Bugs found and fixed

These classes of bugs were found by this testing and are fixed:

AreaBug
ReplicationA replica restarted while receiving writes could apply some of them twice: list elements came back doubled, and a repeated stream entry stopped startup
Hash field TTLA hash whose fields had all expired stayed visible to TYPE, EXISTS, SCAN and KEYS, and made other writes reply WRONGTYPE, until a background sweep reached it
CheckpointsSAVE with two shards could wait up to two minutes when a checkpoint write failed, instead of failing at once as with one shard
RollbackA failed script or refused MULTI could drop a key from a running checkpoint, so a restart lost it
RollbackThe same rollback path could lose a hash's field expiry, so expired fields were returned
TransactionsA command refused while queued in MULTI did not abort the transaction; EXEC ran the rest
CheckpointsRELEASE of a lease or semaphore during a checkpoint could write the wrong value into the snapshot
Memory limitDeletes and other commands that only free memory were refused on a full noeviction store
WAL failuresAfter a failed always sync, a write the client was refused could still reach a checkpoint and come back after a restart
WAL failuresA SAVE or segment rotation whose sync failed left refused always writes on disk, so a restart replayed them
WAL failuresWrites forwarded between shards in one batch could be acknowledged although their log records had been cut
Power lossA final WAL segment whose header never reached disk stopped startup with "invalid WAL magic" instead of being dropped as a torn tail
StartupLoading a checkpoint with hash field expiries or semaphores used the wall clock instead of the replay clock, so startup could fail
ReplicationA replica slot was not freed when the link dropped, so the primary refused new replicas once the limit was reached
ReplicationAfter a primary restart, frames the old link had queued arrived again on the new link; the replica refused them and stopped following for good. It now skips them and takes a fresh copy on a real gap
Process killUnder everysec, a write could be acknowledged while its record still waited in memory behind another connection's open WAL group, so a kill -9 lost it
Blocking popsA pop served by a push whose always sync then failed still returned the element, although the push was refused and gone after a restart
TransactionsA MULTI forwarded to another shard could still run part of its commands after its batch's WAL sync failed
WAL failuresA forwarded push that only fed a waiting pop lost its reply when its batch's sync failed, although nothing it wrote needed the log

Known limits

Not coveredNotes
FailoverPromotion is manual and is not part of these runs
Power loss beyond WAL contentsDirectory entries and checkpoint files are not part of the power-loss model
Network partitionsReplica tests kill and restart processes; they do not cut or delay the link alone
Part of the command surfaceThe checker's workload has no MOVE, SWAPDB, multiple databases or JSON commands
PlatformsDisk faults, power loss and torn writes use an LD_PRELOAD shim, so they run on Linux only
Disk faults on replicasReplica configurations do not inject disk faults
Hot keys with appendfsync alwaysA hot-key write is applied to the shared hot store before its batch is synced. If that sync then fails, the client gets an error, but readers can still see the value until a restart; checkpoints stop until then. Writes to a log that has already failed are refused before they are applied. The checker has no hot-keys configuration

Run it

Linux, Python 3 and a C compiler (for the shim) are needed. A one-hour run over all configurations:

cargo build --profile release-fast --bin ruvio
python3 scripts/model_check.py --seed 1 --duration 3600 --config all \
    --bin target/release-fast/ruvio --results target/model-check --keep-going

Options, the mutation runner and how to read a failure are in the test guide.

Docker resilience · 2026-10-03

Environment: Docker Engine 29.8.0, Linux/aarch64 container, image ruvio:resilience-test (digest starts 56dcb352). Method: five bounded scenarios: tmpfs disk full, WAL directory permissions, SIGKILL, replica partition/catch-up and a 30-second mixed-command soak. Results:

ScenarioObserved result
tmpfs ENOSPC9,216 acknowledged writes recovered after clearing the fault and restarting; fault-time writes returned MISCONF
WAL permission denial3 acknowledged writes recovered after permission repair and restart; fault-time writes returned MISCONF
Process SIGKILL100/100 acknowledged writes recovered in this scenario
Replica interruptionAll 200 writes present after catch-up and manual promotion; catch-up 0.371 s
30-second soak48,413 iterations / 145,239 SET/GET/INCR commands

Reproduce: ./scripts/test.sh --docker-resilience. Limit: Docker Desktop Linux VM on the tested host, not bare-metal Linux or host-power-loss proof; promotion was manual and is not partition-safe automatic failover. The JSON report was in ignored target/ output and is not publicly archived.

Native in-flight process kills · 2026-10-03

Environment: Apple M4 Pro, macOS. Method: three randomized process kills during pipelined writes for each of everysec and always. Result: six of six trials restarted with a continuous key prefix and all client-observed acknowledged writes present; recovered key counts were 297/576/810 (everysec) and 592/621/320 (always). Limit: process termination only; native filesystem faults and host power loss remain untested. Run ./scripts/test.sh --native-resilience for a new local report.
