One process · RESP · shared nothing

One RESP process. The shard that owns the key does the work.

Lease, semaphore, a capped counter, version, limit, once, an idempotent reserve, take, sliding expiry, delayed stream delivery, and a change feed stay in that process, on that shard. You do not add Redis, Garnet, Dragonfly, or a side tool for those jobs.

Eleven jobs on the owner shard

A feature stores bytes only when a key uses it. GET, SET, and INCR do not look it up.

LEASE · RELEASE

A token for one key. Expiry and RELEASE keep the sequence while the key exists. Deletion or data loss can restart it, so an external resource needs its own fencing. In WAL-backed modes, each grant is written to the write-ahead log (WAL).

#coordination#leases

SEMAPHORE · RELEASE

Lets up to max holders share one key. Each holder has its own TTL, so a crashed worker frees its slot when the TTL runs out. RELEASE frees one token. The key is removed when the last holder leaves. A token from an old key cannot release a new holder.

#concurrency#workers

INCRBY · MAX

INCRBY key n MAX limit adds n only if the result stays at or below limit. If it would go over, the reply is a null bulk and nothing changes, neither the key nor the WAL. Plain INCR works as before.

#capacity#counters

SETV

The write succeeds only if the caller still has the current version. Two clients cannot both change 12 to 11. Only keys written with SETV carry a version.

#conditionalWrite#lostUpdate

LIMIT

A fixed time window on one key. It returns the remaining allowance, or a null bulk when the window is full. The window is the key's deadline, so an unused window expires.

#rateLimiting#quota

ONCE

The first call returns 1 and keeps the key until its TTL ends. Later calls return 0 and do not extend the TTL. After the deadline, the next call counts as the first again.

#dedupe#once

IDEM

Reserves a request, rejects a fingerprint conflict, and replays the stored result once the request completes. Completion checks the owner and keeps the original deadline. Outside side effects, such as a payment, still need their own deduplication or transaction.

#idempotency#payments

TAKE

Subtracts from an integer only when the key holds enough. If it does not, the reply is a null bulk and the key stays unchanged.

#inventory#stock

GETEX

Returns the string and sets its deadline to now plus the given milliseconds. GET does not change the deadline.

#sessions#slidingExpiry

XADD DELAY

The entry is stored right away. XREADGROUP waits until the delay passes. XREAD can still see the entry. The hold is written to the WAL only when a delay is set.

#delayedJobs#queues

CHANGES

CHANGES START turns on a feed of up to 1024 notes for later SET, SETV, LEASE, and RELEASE writes on that shard. Before START, those writes do one null check. The feed is empty after a restart.

#changeFeed

A write is checked, appended, then applied

Durability is named at startup: memory, snapshot, everysec, or always. If the log cannot take the record, the key stays as it was and later writes return MISCONF. Durability

Memory stays with the key you wrote

An entry is the value. TTL lives in a separate ring, so a key without expiry does not carry a deadline. On this machine, 20,000 lease keys added about 3.6 MB. 20,000 versioned 64-byte strings added about 7.2 MB, body included.

Clients that find the shards

Point Ruvio.Client or ruvio-client at one address. They read CLUSTER SLOTS, open one socket per shard, and follow MOVED. Each shard has its own WAL. PING still answers PONG. Clients

Start

A default server listens on 127.0.0.1:6379. The operator UI is a second process on port 8080.

docker pull salihcantekin/ruvio:linux
docker run --rm -p 6379:6379 \
  -e RUVIO_REQUIREPASS=change-me \
  -v ruvio-data:/data \
  salihcantekin/ruvio:linux
