What has been tested

Ruvio has protocol, compatibility, persistence, recovery, client, and runtime-safety checks, plus dated performance measurements. This page separates test coverage from evidence of a recent run—and calls out the production questions that remain open.

Automatic and manual checks are distinct. The short pr-gate.yml runs for pull requests and pushes to main. Extended ci.yml, integration-package, and Pages deployment workflows require manual dispatch. Coverage does not imply a passing run on the current commit.

Explore the evidence

Each topic shows test conditions, measured outcomes, limitations and links to the underlying methodology. These are dated observations—not an all-workloads capacity, durability or compatibility guarantee.

Run the tests

Clone the repository and run the portable test entry point from its root. The default runs formatting, all Rust targets, and a store smoke example; resilience scenarios are opt-in.

EnvironmentCore checksOptional resilience checks
macOS / Linux / WSL./scripts/test.sh./scripts/test.sh --native-resilience and ./scripts/test.sh --docker-resilience
Windows PowerShell.\scripts\test.ps1.\scripts\test.ps1 -NativeResilience and .\scripts\test.ps1 -DockerResilience

Clippy is opt-in with --clippy or -Clippy. Docker tests require Docker Engine with Linux containers and tmpfs support. For WSL filesystem tests, keep the checkout and data under the Linux filesystem rather than /mnt/c. See the full test guide for prerequisites and limitations.

The 30-second mixed SET/GET/INCR soak completed 48,413 iterations (145,239 commands). Mutations during the injected filesystem failures returned MISCONF; after the fault was removed and Ruvio restarted, acknowledged keys were verified. Scenario details and rerun instructions.

These tests cover process and filesystem behavior inside a Linux container. They do not simulate host power loss or prove physical storage flush semantics. Docker Desktop's Linux VM is not bare-metal evidence. Docker's filesystem faults have not been run against a native macOS filesystem.

Performance and memory evidence

The public 17-command Redis comparison and one-million-string and equal-pass memory probes show the 2026-10-07 conditions, numbers, limits and downloadable raw JSON on this site; a GitHub account or repository access is not needed to read them.

Other dated records include Docker Desktop workloads and a Cherry EPYC 7313P Linux run. Laptop and Docker results are not production-hardware claims.

Still needed for production confidence

  • Host power-loss and production-like physical-storage flush testing.
  • A 24-hour mixed-workload soak remains unvalidated and is not part of the current test plan.
  • Native macOS disk-full and permission-denial tests outside Docker Desktop's Linux VM.
  • Published, repeatable bare-metal Linux latency and throughput measurements.
  • Repeated failover drills with measured recovery time; replica promotion is currently manual.
  • Signed build provenance in addition to checksums and the generated SBOM.

Use the testing evidence guide and release gates to track these as the test plan grows.

Test evidence is dated and scoped: a passing container scenario is not a durability certification.
